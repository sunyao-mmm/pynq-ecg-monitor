## 2. 协作方式：四步闭环

整个项目下来，有效的协作几乎都遵循同一个节奏：

1. **描述现象，而不是描述猜测**。
   例如"波形只有 30 个计数、间隔 0.55 秒"，而不是"我觉得滤波器有问题"。
2. **先要证据，再要结论**。
   模型每次给出判断，都同时给出"怎么验证这个判断最便宜"。比如"抓 2000 点，只算首尾时间，别把初始化算进去"。
3. **用最小代价的测试证伪**。
   优先选"不重新出比特流就能做"的验证；必须动硬件时，一次只改一个变量。
4. **把结论固化成脚本或检查项**。
   每解决一类问题，就多一个 `.py` 或少一条踩坑记录，不再依赖记忆。

## 3. 七个典型案例

### 案例一：时序不收敛（WNS −25.86 ns，506 个失败端点）

**现象**：综合能过，实现后时序崩了，失败端点分成三簇：argmax 环 −25.9 ns、陷波器内部 −10.5 ns、FIR 输出寄存器 −8.6 ns。

**判断**：不是某一处写错，而是 100 MHz 下整条串行 MAC + 21 点 argmax 的组合路径太长。

**选择**：与其把每一级都拆成流水线（改动大、验证成本高），不如把 PL 时钟从 100 MHz 降到 20 MHz——每采样点可用 8 万个时钟周期，串行结构完全够用。

**结果**：时序收敛，功能不变，代价是延迟增加（对 250 Hz 的心电无影响）。

**收获**：先问"这个设计的真实带宽需求是多少"，再决定时钟。为跑高分时钟而做流水线，是拿验证时间换虚荣指标。

### 案例二：采样率只有 50 Hz

**现象**：源码里 `CLK_PER_SAMPLE = 80000`（20 MHz / 250 Hz），实测进样率却只有 50 Hz。

**判断**：不是 RTL 算错，而是**方块图里的参数覆盖了源码常数**——BD 实例带着旧的 `CLK_PER_SAMPLE` 值。

**验证**：抓 711 点计时，229 Hz；核对 BD 的 `CONFIG.CLK_PER_SAMPLE`。

**结果**：改正 BD 覆盖值后恢复到 229–235 Hz。

**收获**：在"RTL 常数 / BD 参数 / 实际时钟"三者之间，**BD 参数优先**。改源码不改 BD，等于没改。

### 案例三：实时采集一直是常数

**现象**：ROM 通路正常，切到 ADS1292 后波形是一条 +11085 的直线，自检字里帧数却一直在涨。

**判断过程**：先排除 SPI（帧数在涨）、再排除寄存器配置（ID 能读回）、最后发现——**3.5 mm 导联插头从来没有插进模块的孔里**。

**结果**：插上后立刻出现 ±7 计数的信号；把通道 2 增益从 1（`CH2SET=0x10`）改为 6（`0x00`）后，QRS 幅度达到 45–65 计数。

**收获**：模型再强也看不见"线有没有插"。**物理事实必须由人提供**，包括最不起眼的那些。

### 案例四：毛刺处理从硬件屏蔽改为显示层处理

**现象**：波形上反复出现 2–4 个采样点宽的尖刺（CLT 冲到 3000，正常心跳只有 600），把自适应阈值顶高，后面几拍全部漏检。

**方案演进**：

1. 第一版尝试在硬件里把毛刺替换为中值，这会改变原始数据，无法区分真实高频 QRS 与伪迹。
2. 第二版尝试硬件屏蔽短毛刺，但门限依赖波形，换电极或换人后容易误删真实波形。
3. 最终方案删除 `clt_qrs.v` 内的毛刺屏蔽，PL 检测器只保留 CLT、阈值和不应期；网页仅在绘图数据上做短尖刺清理，R 峰判据仍基于 PL 结果和固定局部峰峰值门槛。

**收获**：算法链与显示层要分开。显示层可以改善可读性，但不能让"图看起来干净"掩盖原始检测状态。

### 案例五：CLT 曲线很漂亮，硬件一个 R 峰都不给

**现象**：实时波形的 CLT 曲线上 12 拍清清楚楚（峰值约 750），但 `R 峰标志个数 = 0`、`beat_count = 0`。

**判断**：阈值 = 0.4 × est，est 是从开机后前 30 个采样点里学的；那 30 个点正好落在 FIR 与前端的**启动瞬态**上，学到的值远大于真实心跳，阈值被顶到天上，要靠"每 250 点重学一次"慢慢降下来——上一版正是从 5.3 秒才开始出标记。

**解决**：加 `SETTLE` 参数，跳过启动瞬态再学阈值；并且**按数据源区分**：ROM 回放给 0（第一拍就要能判出来，自检才对得上），实时通路给 96。

**收获**：同一个参数在两条通路上可能有完全不同的最优值。**不要用一个常数去伺候两种数据源**。

### 案例六：导联检测读数正好是反的

**现象**：电极接好、波形漂亮时，寄存器报 `LOFF_STAT = 0x7f`（全部脱落）；把电极拔掉、波形变成直线时，反而报 `0x00`（全部正常）。

**判断**：不是位定义理解错，而是**读取时机错**——在"刚配完寄存器、芯片还没开始转换"的那一刻读，输入端共模还没建立，比较器自然乱报。

**改进**：改为读取**每一帧数据自带的状态字字节**，它是芯片每 4 ms 现算的，反映当前状态，而且不需要额外发命令、不打断数据流。

**保留意见**：该字节的位定义在不同版本手册中写法不完全一致，因此界面只显示原始值与置位情况，不硬下"哪根线断了"的结论——**没验证过的结论不写进报告**。

### 案例七：网页运行几十秒后波形和 CLT 错位

**现象**：静态采集正常，网页连续运行后波形逐渐变乱；ROM 端运行约 42 秒后也能复现。

**判断**：静态采集到长度后停止，从未经历缓存写入回绕；连续模式回绕时，CLT 写指针先到地址 0，而下一个波形字仍从上一对地址开始，导致波形和 CLT 不再是同一采样点。

**验证**：把 4096 字 RAM 的读写映射单独仿真，连续覆盖 4 次回绕，同时检查波形字、CLT 字和写指针。修复后 `tb_ring_memory` PASS。

**结果**：连续环形缓存的地址在最后一个 CLT 字写完后回到地址 1，不再提前写地址 0；record 208 长循环 105 圈仍保持每圈 4 拍。

**收获**：只测"一次采集"发现不了长时间运行错误。只要产品界面是滚动显示，就必须专门测试回绕、覆盖和停止/重启边界。

## 4. 判断修正日志

工程里比"答对"更重要的是"改得快"。以下是本项目中被明确推翻的判断，全部留有依据：

| 曾经的判断 | 推翻依据 |
|---|---|
| AR5 引脚损坏 | 换脚后 CS/DRDY 均正常，是接线与引脚定义问题 |
| 方块图连线错误 | 逐条核对 BD 网络，连接本身正确 |
| 烧的是旧版比特流 | 源文件 MD5 与工程引用一致 |
| 把右腿驱动输出接到输入电极以闭合回路 | **危险操作，已撤回**：可能损伤模块，后续的间歇断链可能与此有关 |
| 红绿短接后基线回到 0 说明环路正常 | 实为缓存里的旧数据/ROM 数据，不是实时信号 |
| 毛刺是 SPI 读坏了一帧 | 宽度与重复性分析后，更可能是电极/导联接触瞬变 |

这份表是刻意保留的：**它证明整条链路有纠错能力**，而不是一路"顺着说"。

### 5.2 重建流程检查清单（每次改 RTL 都走一遍）

1. 替换源文件 → 2. IP Status 中 Refresh module reference → 3. Reset Output Products → 4. Generate Output Products（Global）→ 5. 核对 BD 参数没有被旧值覆盖 → 6. Generate Bitstream，确认 WNS ≥ 0 且失败端点为 0 → 7. 导出与 `.bit` 配对的 `.hwh` → 8. 成对上传 `.bit/.hwh` 和网页文件 → 9. 重启 Jupyter/网页服务 → 10. 先跑 ROM 自检，再跑实时。

### 5.3 故障对照表

| 现象 | 优先怀疑 | 一分钟验证 |
|---|---|---|
| 波形是一条常数直线 | 导联未插 / 输入悬空 | 看自检字帧数是否在涨 |
| 帧数为 0 | DRDY / 白座接触 | 重插排线，看 CLT_NOW 是否变化 |
| 进样率明显低于 250 Hz | 首段含初始化时间 | 只算首尾采样点之间的时间 |
| bpm 忽大忽小 | 阈值被毛刺顶高 | 看 CLT 是否出现远超正常值的尖峰 |
| 图上一条 2.15e9 的平线 | CLT 字最高字节被当成数值 | 检查是否用了配套版本的显示脚本 |

## 6. 有效与无效的用法

**有效的**：

- 给现象、给数字、给截图，让模型去提假设；
- 要求"先给验证方法，再给结论"；
- 让模型写**可执行的检查脚本**，而不是写解释；
- 明确说"这个判断如果错了，代价是什么"，逼出更保守的方案。

**无效的**：

- 问"为什么不好使"而不给任何现象；
- 让模型猜硬件状态（它看不见板子）；
- 一次改五个地方，最后不知道是哪一处起的作用；
- 把"模型说对"当成"验证过"。

**边界**：模型能设计验证方法、能读波形、能算数字，但**不能代替示波器和逻辑分析仪**，也不能替你判断"这根线到底插没插"。物理世界的事实只能由人提供，这也是整份记录里最重要的一条。

## 8. 脱敏交互摘录

本节保留项目中最关键的用户提示、模型判断、人工验证和最终修正。该部分与前述案例复盘互为索引，不引用个人环境或未脱敏数据。

### 8.1 系统连续运行后波形与 CLT 错位

**日期**：2026-10-24 至 2026-10-25

**用户提示（摘录）**

> ROM 和实时采集跑着跑着还是会出现波形越来越乱的现象，分析一下。  
> 大概 42 秒后 ROM 端开始波形混乱。

**模型回答摘要**

模型将问题限定在连续模式：静态采集达到长度后停止，不会经历写地址回绕；网页连续模式必须覆盖旧数据，因此应优先检查波形字、CLT 字和写指针是否在回绕点失去对齐。

**人工验证**

将 4096 字 RAM 的读写行为单独建模，连续覆盖 4 次回绕，同时检查波形字、CLT 字和写地址。旧逻辑在回绕后提前写入地址 0，导致后续采样点的字对错位。

**最终修正**

连续模式写完最后一个 CLT 字后，将下一个波形字地址回绕到 1，而不是 0。新增 `tb_ring_memory` 和 `tb_ecg_continuous`，两者均通过；record 208 连续运行 105 圈，每圈稳定检出 4 拍。

### 8.2 T 波被误判为 R 波

**日期**：2026-10-25

**用户提示（摘录）**

> CLT 红心总是标在 T 波上这个问题，用通俗易懂的话给我分析几个解决方案。  
> 但如果第一拍看出来是 T 波，后面不是全乱了吗？

**模型回答摘要**

模型指出，不应仅通过提高全局阈值解决 T 波误触发，因为低幅室早也会被一并压掉。应优先利用时间约束，通过不应期和长 RR 恢复窗口区分 R 波与 T 波。

**人工验证**

回看 CLT 曲线和硬件 R 标志，确认部分误报发生在主 R 峰之后的 T 波窗口；全局抬高阈值会明显降低宽 QRS 的召回率。

**最终修正**

保持主阈值 `THR_NUM=13`，使用 `REFRACT=100` 抑制 R 波后约 400 ms 内的重复触发；仅在长 RR 间隙的预期下一次心搏附近启用 `LOW_THR_NUM=12`。

### 8.3 毛刺导致后续连续漏检

**日期**：2026-10-24

**用户提示（摘录）**

> 我重新跑了一个，这个毛刺也太多了。

**模型回答摘要**

模型比较了“用中值替换毛刺”和“仅标记异常”两种方案，认为直接改写原始采样值会掩盖真实波形，也可能删除高频 QRS；应先从电极接触和导联瞬变排查物理原因，同时把网页显示去毛刺与硬件检测判据分开。

**人工验证**

统计尖刺宽度、前后原始值和重复性，发现多数尖刺宽度短于正常 QRS，并在电极接触变化时增多。

**最终修正**

删除硬件侧毛刺替换逻辑；网页仅对绘图序列做短尖刺清理；实时 R 峰使用固定局部峰峰值门槛，不再使用会被大伪迹抬高的全局中位数。

### 8.4 ROM 正常但实时波形畸形

**日期**：2026-10-25

**用户提示（摘录）**

> 实时出的波形很畸形，分析一下原因。  
> ROM 端是正常的，但是实时采集端不太正常。

**模型回答摘要**

模型建议按“数据是否新鲜、格式是否正确、电极是否稳定”三层排查：先比较 ROM 与实时模式的 ID、帧数、写指针和波形范围，再检查电极接触与供电。

**人工验证**

ROM 通路保持正常；实时模式中按压电极和重插连接器后波形明显改善，同时确认部分大尖刺符合接触瞬变特征。

**最终修正**

保留硬件检测链不变，增加信号质量辅助判断；信号不可信时网页显示异常并暂停 BPM/RR 输出。

### 8.5 未接电极时仍出现噪声

**日期**：2026-10-25

**用户提示（摘录）**

> 现在我根本没接电极片，没插插座。  
> 这个现象有什么后果？怎么解决这个现象？

**模型回答摘要**

模型判断输入处于悬空高阻状态，拾取环境工频和人体耦合噪声属于正常物理现象，不能将此时波形当作有效心电；应先通过帧数、芯片 ID 和信号质量判断区分通信正常与输入无效。

**人工验证**

连接电极后噪声形态和幅值明显变化，确认悬空输入是主要原因之一。

**最终修正**

信号质量规则增加低幅、过载、高频噪声和明显基线异常判断；不可信时停止输出 BPM、RR 和累计心搏。

### 8.6 采样率不是标称 250 Hz

**日期**：2026-10-19 至 2026-10-20

**用户提示（摘录）**

> 我们不是还为了这个修改了 50 Hz 陷波器？

**模型回答摘要**

模型建议区分“包含 Python 回读开销的吞吐量”和“纯采样率”：固定采集 N 点，只计时到 `cap_done`，用 `N/Δt` 计算实际进样率，再据此检查 50 Hz 陷波频点和 BPM 换算。

**人工验证**

排除回读开销后，实测 ADS1292 的代表进样率为 243.65 Hz。该偏差会使按 250 Hz 设计的陷波频点偏移，并使硬件 BPM 系统性偏高。

**最终修正**

按 243.65 Hz 重新计算 50 Hz 陷波系数；PS 端按 `243.65/250` 修正实时 BPM/RR。ROM 通路仍使用 250 Hz 标称时基。

### 8.7 MIT-BIH 验证时间轴不可信

**日期**：2026-10-26

**用户提示（摘录）**

> 时间轴不可信的 MIT 记录是为什么不可信，这个方面会对整个项目有影响吗？

**模型回答摘要**

模型指出，“时间轴不可信”是当前验证脚本的自动筛选结果，不等同于数据库标注错误。固定读取记录首通道会对 record 114 的 V5 通道产生错配；其他记录还受 ATR 特殊标注解析和 90% 对齐阈值影响。

**人工验证**

使用官方 MIT-BIH Arrhythmia Database 1.0.0 重跑 23 条记录：14 条通过可信检查，汇总 Se 为 98.21%、PPV 为 98.43%；其余 9 条保留在完整表中，但不计入总体指标。

**最终修正**

报告明确写成“14 条时间轴可信记录”，不再表述为全库结果；验证脚本同步最终双阈值逻辑，并将完整 23 条记录保留在 `data/mitbih/verification_results.md`。
